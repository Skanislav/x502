# Codebase Coverage Design

## Goal

Raise automated test coverage for x502 to near 100% on first-party runtime code, module by module, while keeping the measurement honest. The strict target applies to code we own and execute in normal runtime paths. Generated artifacts, deployment scripts, CLI boot entrypoints, and live external-service-only paths are documented exclusions rather than padded with brittle tests.

## Scope

Included in the coverage target:

- `contracts/src/**/*.sol`, especially `BountyVault.sol`, `GitHubFactReceiver.sol`, `Attestations.sol`, and test mocks that encode behavior used by integration tests.
- `packages/shared/src/claim-id.ts`, `packages/shared/src/eip712.ts`, and exported type/name constants.
- `packages/verifier-agent/src/server.ts`, `sign.ts`, `decide.ts`, `policies/claude.ts`, and wallet-provider logic that can be exercised without real CDP credentials.
- `packages/coordinator/src/server.ts`, `pipeline.ts`, provider interfaces, and adapters whose behavior can be tested with fake clients.
- `packages/web/lib/**/*.ts` and reusable behavior extracted from `packages/web/app/page.tsx` where extraction improves testability without changing UX.
- `demo/src/**/*.ts` and `demo/scripts/derive-commitment.ts`.
- Testable decision logic extracted from `chainlink/source.js`.

Excluded from strict thresholds:

- `packages/shared/src/abis.ts`, generated bytecode and ABI output.
- `contracts/script/Deploy.s.sol`, because meaningful verification is deployment/preflight oriented and environment-bound.
- `packages/*/src/main.ts` boot files, where coverage would mostly assert environment plumbing and process startup.
- `packages/web/app/page.tsx` as a JSX rendering surface after behavior is extracted into tested helpers. It remains covered by manual UAT or future Playwright tests; the assertable state mapping and form logic live in library modules.
- Real network paths for CDP, Chainlink Functions, x402 facilitators, GitHub, Base RPC, and Anthropic. These remain integration-test candidates behind explicit credentials, not default coverage requirements.
- Third-party vendored dependencies under `contracts/lib`, `node_modules`, build output, caches, and coverage output.

All strict-threshold exclusions belong in this Scope section. Divergences between current implementation and design intent belong either here, when excluded, or in the current-behavior test convention below when pinned by tests.

## Baseline

Fresh baseline after restoring workspace dependencies:

- `pnpm test` passes: Solidity tests and TS tests for `@x502/shared`, `@x502/verifier-agent`, and `@x502/coordinator`.
- `pnpm --filter @x502/demo test` passes.
- `pnpm --filter @x502/web exec vitest run` fails because the web package currently has no test files.
- `pnpm --filter @x502/shared exec vitest run --coverage` fails because `@vitest/coverage-v8` is not installed.
- `cd contracts && forge coverage --report summary` reports `76.44%` total lines. Core contracts are already much higher: `BountyVault.sol` is about `91%` lines and `GitHubFactReceiver.sol` about `93%` lines. Global coverage is dragged down by `Deploy.s.sol` and simple mocks.

## Architecture

Use a measured first-party runtime coverage model:

1. Add coverage tooling and scripts so coverage can be collected consistently.
2. Add focused tests per module using each package's native runner.
3. Extract only the minimum pure functions needed to make hard-to-test runtime behavior directly testable.
4. Set coverage thresholds after the first coverage pass confirms stable denominators.

Solidity coverage continues to use Foundry. TypeScript coverage uses Vitest with the V8 provider. Web tests use Vitest for library and extracted behavior first; component tests can be added with React Testing Library only if library-level tests leave important behavior uncovered.

## Current Behavior Test Convention

Tests that pin known-divergent behavior must be recoverable when the intended behavior is implemented. Use both conventions:

- Prefix the test name with `currentBehavior_`.
- Add a short header comment above the test or suite citing the relevant `USER_FLOW.md` "Current vs. intent" callout.

This applies at minimum to:

- `currentBehavior_payoutAcceptsStatusZero`, where `BountyVault` accepts a fact blob with `status=0` when verifier signatures are valid.
- `currentBehavior_ghAuthorBindingParsedButNotEnforced`, where `chainlink/source.js` parses the `<!-- x502:0x... -->` marker but the vault never enforces the parsed wallet binding.
- `currentBehavior_commentsNotFetchedForCommitmentOrEvidence`, where verifier policy tests pin that GitHub comments are not fetched for commitment markers or repro/dedup evidence.

When production behavior intentionally changes, update or remove the matching `currentBehavior_` tests in the same change.

## Foundry Dependency Baseline

Decision: treat the current `contracts/foundry.lock` additions for `chainlink-brownie-contracts` and `openzeppelin-contracts` as the deterministic Forge baseline because they match the checked-out submodule revisions. The first implementation step before coverage commits is a separate `chore(contracts): pin forge dependency lockfile` commit containing only that lockfile change.

After that baseline commit, coverage work should run against the committed lockfile. Any later Forge lockfile change must be reviewed as a dependency-baseline change, not bundled into unrelated test coverage commits.

## Module Plan

### Contracts

Target the remaining untested branches in `BountyVault.sol` and `GitHubFactReceiver.sol`.

Coverage additions:

- `configureRepo` rejects `threshold == 0`.
- `deposit` rejects unconfigured repos.
- `withdraw` rejects insufficient balance and succeeds for the owner.
- `payout` rejects length mismatches.
- `payout` rejects `PriceUnderflow`.
- `priceOf` covers `Report`, `Triage`, `Fix`, and `DocsTests`.
- `trustedAgentsOf`, `thresholdOf`, `outcomeFeeOf`, `domainSeparator`, and `hashAttestation` view behavior is pinned.
- `currentBehavior_payoutAcceptsStatusZero` documents that `BountyVault` accepts a fact blob with `status=0` if verifier signatures are valid.
- `GitHubFactReceiver` ownership transfer, source update, authorizer update, source/config events, secrets branch, zero external ID argument, and getFact empty state are covered.
- Mocks get small tests only where they represent behavior relied on by integration tests.

`Deploy.s.sol` is not part of the strict coverage target. Deployment readiness should be validated by explicit deploy/preflight checks, not unit coverage.

### Shared

Existing tests cover claim ID and commitment basics. Add tests for:

- `Kind` and `KindName` mapping integrity.
- `attestationDomain` fields.
- `attestationTypedData` shape and message preservation.
- Signature recovery against `attestationTypedData`, matching verifier and vault expectations.
- More repo slug vectors for case sensitivity and `github.com/` prefix behavior.

### Verifier Agent

Add tests around input validation, policy behavior, and wallet provider branches.

Coverage additions:

- `/verify` validation branches for bad `repoId`, `externalId`, `kind`, `recipient`, `deadline`, and `factHash`.
- Unknown `repoId` returns `404` when resolver returns `undefined`.
- Response shape includes reason, stringified deadline, signature, agent ID, and attestation fields.
- `signAttestation` delegates through `attestationTypedData` and returns the configured agent ID.
- `AcceptAllPolicy` and `RejectAllPolicy` return stable reasons.
- `ClaudePolicy` covers bad repo slugs, GitHub fetch failures, issue context, PR context, label extraction, commitment success/failure, missing reveal, no text response, accept JSON, reject JSON, and malformed JSON.
- `ClaudePolicy` request-shape assertions verify the SDK call includes `model: "claude-opus-4-7"`, `thinking: { type: "adaptive" }`, schema-backed `output_config` with effort, system prompt `cache_control: { type: "ephemeral" }`, and user-prompt fields including `Claim type`, `Recipient`, and `Commitment verified:`.
- `ClaudePolicy` current-behavior tests that pin missing GitHub comment fetching use the `currentBehavior_commentsNotFetchedForCommitmentOrEvidence` convention.
- `EnvKeyWalletProvider` validates account wiring and signing behavior.
- `pickWalletProviderFromEnv` covers provider selection, CDP mode selection, network mapping, faucet flag, default account names, and error branches.
- `CdpWalletProvider` is tested with mocked CDP objects for EOA and smart modes, including faucet best-effort branches and smart-wallet unsupported `signMessage`/`signTransaction` behavior. No real CDP credentials are used in default tests.

`main.ts` boot behavior is excluded from strict thresholds. It can be covered later by a small integration boot test if the entrypoint is refactored to export `chainFromId` and `main`.

### Coordinator

Existing tests cover most server and pipeline paths. Add adapter and edge coverage:

- `StaticRepoRegistry` add/resolve/resolveSlug and overwrite behavior.
- `FetchVerifierClient` serializes `bigint` fields, optional commitment reveals, parses successful JSON, parses rejection `reason` and `error`, and falls back when error JSON is invalid.
- `ViemVaultWriter` maps attestations to `agentIds` and `signatures`, calls `simulateContract` before `writeContract`, waits for receipt, and propagates simulation/write failures.
- `ViemFactProvider` start idempotency, stop behavior, request argument mapping, immediate-ready fact path, event-delivered fact path, unrelated events ignored, missing blobs ignored, timeout rejection, and pending cleanup.
- `X402PaymentGate` maps route options and facilitator URL into `paymentMiddleware` using a module mock.
- `buildX402Fetch` delegates to `wrapFetchWithPayment` using a module mock.
- `buildCoordinator` adds tests for invalid JSON if Hono exposes that path cleanly, numeric `externalId`, numeric reveal fields, pipeline crash state becoming `410`, and failed poll response shape.
- `runClaimPipeline` adds coverage for accepted verifier ordering when returned out of order, all verifiers rejecting, verifier timeout counted in error detail, and `updatedAt` transitions.

### Web

The web package currently has no tests. Start with low-friction tests that do not require a browser:

- `formatUsdc` covers zero, cents, whole dollars, truncation from 6 decimals, and large values.
- `shortHash` covers short strings and long hashes.
- `basescanTx` covers Base Sepolia default and Base mainnet.
- `CoordinatorClient.postClaim` covers success, `402 Payment Required`, non-OK responses with body text, and request JSON shape.
- `CoordinatorClient.poll` covers status/body return shape.
- Extract `mapPoll` and claim form helpers from `page.tsx` into a small testable module, then cover paid/failed/verifying/ready states and commitment-preview guards.
- Keep the remaining JSX in `page.tsx` outside strict coverage thresholds unless future Playwright or component tests are introduced deliberately.

Only add React component testing dependencies if the helper extraction leaves critical UI behavior untested. Initial component tests should be smoke-level and avoid brittle visual assertions.

### Demo

Existing `splitEvenly` tests are present. Add or confirm coverage for:

- Input validation for non-integers, non-positive bucket counts, and negative totals.
- Zero total, exact division, remainder distribution, and `n > total`.
- Extract argument parsing and commitment derivation from `derive-commitment.ts` into a pure helper and test it directly.
- Keep one thin CLI smoke test for success output and one missing-argument usage test, avoiding broad child-process coverage.

### Chainlink Source

`chainlink/source.js` currently runs directly in the Chainlink Functions sandbox. To test it without a DON:

- Extract pure decision logic into an exported ESM helper, for example `chainlink/source-core.js`.
- The extracted core must be pure JavaScript with no `ethers` dependency and no `https://esm.sh/...` imports so it can run under Node's Vitest.
- Keep the uploaded `chainlink/source.js` self-contained because `Deploy.s.sol` reads it as inline Chainlink Functions source. Generate it from the pure core plus a small DON wrapper so the wrapper can import `ethers` from `https://esm.sh/ethers@6.13.4`, call GitHub through `Functions.makeHttpRequest`, perform ABI encoding, and reuse the tested decision logic without a runtime relative import.
- Test report behavior for accepted labels, rejected labels, mixed string/object label forms, label mask bits, and wallet marker parsing.
- Use `currentBehavior_ghAuthorBindingParsedButNotEnforced` for tests that pin parsing of `<!-- x502:0x... -->` without vault enforcement.
- Test triage label count and `triage-done` mask.
- Test fix behavior for merged/unmerged PRs, closing keyword matching, missing merge SHA, and mergedBlock encoding.
- Test `docs_tests` for test-only, docs-only, both, no relevant files, merged false, file request error, and merge SHA handling.
- Test unknown kind and bad repo slug behavior through the wrapper or a small exported parser.

## Tooling

Add the following tooling in a minimal way:

- `@vitest/coverage-v8` as a dev dependency.
- Package-level `test:coverage` scripts where useful.
- A root `test:coverage` script that runs Forge coverage plus TS workspace coverage.
- Coverage exclude patterns for generated files, boot files, and external-service-only adapters as agreed above.
- A coverage summary artifact path ignored by git.

Thresholds should be introduced after the first implementation pass produces real numbers. The intended final thresholds are near 100% for first-party runtime modules, but per-package thresholds should account for practical exclusions and branch instrumentation differences.

## Review Method

The implementation should proceed with characterization-first TDD:

1. Write one narrow assertion for the behavior under review.
2. Run the narrow test and confirm whether it fails because the behavior assumption was wrong, because a helper has not been extracted, or because the code is missing required behavior.
3. If the implementation already behaves correctly, adjust the assertion to match observed behavior and keep the characterization test.
4. If the assertion is the requirement and production code is wrong, implement the minimal fix.
5. Run the narrow test until it passes, then run the affected package tests.
6. Repeat by module.
7. Finish with `pnpm test`, demo tests, web tests, Forge tests, lint, typecheck, and coverage commands.

Classic red-green-refactor applies to new helper extraction and bug fixes. Existing behavior coverage should avoid forcing artificial failures when the purpose is characterization.

## Risks

- Chasing literal 100% can encourage tests that assert implementation details. The target is near 100% on meaningful first-party runtime behavior.
- Mocking third-party SDK internals can become brittle. CDP, x402, Anthropic, Octokit, and viem mocks should be adapter-bound and behavior-focused.
- `forge coverage` can mutate or expose dependency-lock state when dependencies are not installed. The deterministic baseline is handled by the separate lockfile-pin step above; implementation should keep any later generated dependency churn out of coverage commits unless it is intentionally required.
- Web component tests can add dependency and maintenance weight. Start with helpers and client behavior, then add component tests only where they cover real user workflows.

## Acceptance Criteria

- Root tests pass with `pnpm test`.
- Demo tests pass and are either included in root tests or explicitly covered by the root coverage command.
- Web package has tests and no longer fails with "No test files found".
- Forge coverage and TS coverage commands run without missing-provider errors.
- Coverage reports exclude generated/deploy/live-only surfaces and show near-100% coverage for first-party runtime modules.
- Module-by-module review findings are reflected as tests, code comments only where helpful, current-behavior tests following the convention above, or exclusions recorded in this spec's Scope section.
- No unrelated working-tree changes are included in the coverage commits.
